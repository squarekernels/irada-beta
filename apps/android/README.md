# Irada Android v1 implementation plan

## Building

Open this directory in Android Studio or run `./gradlew :app:assembleDebug`. Use JDK 21 and install Android SDK Platform 37 and Build Tools 36.0.0. Configure your SDK path through an untracked `local.properties` file (`sdk.dir=/path/to/Android/sdk`) or `ANDROID_HOME`.

The pinned build uses AGP 9.2.0, Gradle 9.4.1 and Kotlin/Compose compiler 2.3.20. AGP supplies built-in Kotlin support. Android identifiers and SDK levels are read from `gradle.properties`. The application ID and namespace are `com.ctxaware.irada`, with minSdk 26, compileSdk 37 and targetSdk 37.

Run `./gradlew :app:assembleDebug :app:testDebugUnitTest :app:lintDebug` for local checks. With an emulator connected, run `./gradlew :app:connectedDebugAndroidTest`. The debug APK is generated at `app/build/outputs/apk/debug/app-debug.apk`.

Stage 0 provides the empty Home and Settings shells, native Back navigation and launcher assets. Stage 1 adds a first-run introduction, multiline capture, a single Room draft, explicit resume/discard, and a DataStore introduction preference. Draft text is saved verbatim; no tasks, alarms or network requests are created. Capture shows a local save acknowledgement and a manual retry on failure. Stage 2 adds cancellable preview generation and read-only proposals. System appearance controls the theme. Vector launcher artwork is derived from `design/brand/irada/irada-symbol.svg`; Settings and Back follow the approved 24 dp, 1.8-unit soft-outline treatment. Native system typography is used.

The build template was generated by the official Android CLI on November 20, 2026. AGP and Gradle were then updated together for API 37 support. [AGP compatibility](https://developer.android.com/build/releases/agp-9-2-0-release-notes)


Deliver one stage at a time. Each stage ends with a working deliverable, a repeatable demonstration, and owner review. Stage 0 delivers the first APK. Stage 4 delivers the first complete brain dump → review → approval → offline reopen flow.

The Android plan reference supplies the screen-sized milestones and validation record. The refinements reference informs interaction checks such as whether a suggestion looks accidentally approved, whether Back preserves an edit, and whether actions remain reachable with the keyboard open. Irada’s UX brief defines the product behavior. ## Implementation decisions

- Use one native `:app` module. Compose screens use ViewModels and StateFlow. Room owns tasks and the single pending draft. DataStore owns preferences. Android calls Fastify only for previews, so approval and Home work offline.
- Give each pending batch a stable identity. Approval verifies and consumes that identity in the same transaction that inserts the tasks. Schedule reminders only after commit and reconcile from saved state after interruptions.
- Use the mockups to review hierarchy and interaction. Reserve primary fill for the main action, keep ordinary review rows neutral, label suggestions in words, and use functional symbols on buttons. Check keyboard reachability, system Back, and large text at each screen stage.

## Stage 2 · Preview generation

Capture now provides **Make a plan**, followed by cancellable processing and a read-only proposal. The proposal shows original input, Suggested labels, Anytime/date-only/reminder distinctions and interpretation warnings. No approval action, task storage or scheduling is available yet. Leaving processing cancels the HTTP call; canceled/older results cannot replace a newer request. Rotation keeps the current request/result. Process death restores the Room input and requires a fresh tap; preview results are intentionally in memory until Stage 3.

Every request waits for a new Room save acknowledgement. The request sends the current locale and time zone and the default `09:00` reminder time (configurable preferences arrive in Stage 7). Connect timeout is 5 seconds, read timeout 15 seconds, total HTTP timeout 20 seconds. HTTP redirects and connection retries are disabled. Service/network failure, invalid output and local save failure provide explicit Retry and Edit input. Connectivity recovery never submits automatically.

### Local server connection

Run Fastify from `api` using `npm start`, then run `adb reverse tcp:3000 tcp:3000`. Debug builds default to `http://127.0.0.1:3000/`; forwarding works for an emulator or a USB-connected phone. Only debug builds allow loopback HTTP. Internet and network-state permissions are normal install-time permissions; no local-network permission is needed for the forwarded loopback connection. Input is sent only when the user taps **Make a plan** or **Retry**.

An HTTPS base URL can be supplied with `-Pirada.previewBaseUrl=https://your-host/`. Release builds have no default endpoint and reject cleartext. Until a production service is configured, release preview attempts show a configuration error. The real AI integration is outside Stage 2.

### Isolated device validation

Keep namespace `com.ctxaware.irada` and override only the application ID with `-Pirada.applicationId=com.ctxaware.irada.validation` for tests. This protects the installed app’s draft from Gradle’s test install/uninstall lifecycle.

```sh
./gradlew :app:assembleDebug :app:testDebugUnitTest :app:lintDebug :app:connectedDebugAndroidTest -Pirada.applicationId=com.ctxaware.irada.validation
```

Opt-in HTTP integration checks require `node test-support/preview-server.js` from `api`, an active device network and `adb reverse tcp:3000 tcp:3000`:

```sh
./gradlew :app:connectedDebugAndroidTest -Pirada.applicationId=com.ctxaware.irada.validation -Pandroid.testInstrumentationRunnerArguments.runLivePreviewTests=true
```

Without that argument, the live HTTP tests skip; controller/client and fake-service UI tests remain independent of a running server. Build `:app:assembleDebug` again without the validation property for the review APK. See [validation](../../../validation/android.md) for results and screenshots.

## Stage 3 · Editable batch review

Generated proposals now open **Review your plan** and are saved with the original input in the single Room draft. Each proposal has a stable ID and stored list position. Titles, notes, optional due dates and separate reminder date/time can be edited. **Add a task**, **Remove** (with brief Undo), **Move up** and **Move down** operate on proposals only. An undated item reads **Anytime**.

“Suggested” applies to untouched generated fields; an explicitly changed field reads “Your choice.” Changing a due date does not alter its reminder. Original interpretation notes and batch warnings remain visible. Incomplete titles/overlong fields can be kept as pending edits and are flagged; they do not become tasks. Date/time pickers use calendar dates and local wall-clock values.

Back and **Keep draft and return to tasks** preserve review and return to Home. **Resume draft** reopens review offline without a request. Editor Back/Done keep every typed edit. **Edit original input** first offers **Keep editing** or **Discard proposals**; only explicit discard removes proposal edits, retaining the original input and batch identity. Starting a different capture still uses the existing Resume/Discard choice.

Room schema 2 adds nullable `reviewJson` using an automatic 1→2 migration. Existing text and batch identity stay intact. The payload stores proposal IDs/order, values, per-field edit provenance, original reasons and interpretation warnings. Corrupt review data is not silently cleared. Wait for **Draft saved on this device** before intentionally force-stopping; an abrupt kill before acknowledgement can interrupt the latest write.

There is still no approval action, approved-task table, alarm scheduling or notification permission request. Approval is Stage 4. Stage 3 device tests continue to use `-Pirada.applicationId=com.ctxaware.irada.validation`; the full live suite additionally needs the fixture and `runLivePreviewTests` flag documented above.
