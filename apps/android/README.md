# Irada Android v1 implementation plan

Deliver one stage at a time. Each stage ends with a working deliverable, a repeatable demonstration, and owner review. Stage 0 delivers the first APK. Stage 4 delivers the first complete brain dump → review → approval → offline reopen flow.

The Android plan reference supplies the screen-sized milestones and validation record. The refinements reference informs interaction checks such as whether a suggestion looks accidentally approved, whether Back preserves an edit, and whether actions remain reachable with the keyboard open. Irada’s UX brief defines the product behavior. [Android plan reference](../../ANDROID_PLN_REF.md) · [Android refinements reference](../../ANDROID_REFINEMENTS.md) · [Irada UX brief](../../DESIGN.md)

## Stages and acceptance criteria

| Stage | Deliverable | Acceptance demonstration |
|---|---|---|
| **0 · Installable foundation** | A debug APK built from `apps/android` with the Gradle Wrapper, Kotlin, Compose Material 3, native navigation, an empty Home screen, and Irada’s adaptive launcher icon. Use `#4B32F4`, soft-outline icons, and light/dark themes. | Build in a clean worktree, install on the API 37 emulator, launch in airplane mode, and switch system appearance. Check the launcher silhouette and Home at phone size. Use the Irada mark for branding and a functional plus for capture. |
| **1 · First run and capture** | Introduction and capture screens backed by one Room draft. Returning users can resume or explicitly discard their input. First-time offline users can reach Home and the Settings shell. | Enter multiline text, open the keyboard, rotate, press system Back, kill the process, and reopen. Resume restores the exact input. Starting another capture offers **Resume draft** or **Discard and start over**. The task list stays empty. |
| **2 · Generate a preview** | A cancellable processing screen and read-only preview backed by the Fastify stub. Extend `POST /api/plan-preview` with optional locale, time zone, and default reminder time. Preserve input-only callers. | “Buy groceries” gives Anytime. “Buy groceries tomorrow” adds only a due date. “Remind me tomorrow at 9 to buy groceries” adds a 9 AM reminder. Test across local midnight. Stop the server, retry, cancel a slow request, and restore connectivity. Input survives, stale responses are ignored, and retry requires a tap. |
| **3 · Editable batch review** | Review shows the original input, proposed tasks, editable fields, suggested values, and interpretation warnings. Adding, removing, or editing a proposal updates the pending draft. | Change a date, remove a task, add another, leave Review, and reopen after process death. Edits and order survive. An undated item reads **Anytime**. Suggested values are distinguishable from user choices. Inspect storage and scheduling to confirm zero approved tasks and alarms. |
| **4 · Approval and the first complete loop** | **Approve N tasks** saves the reviewed batch and clears the draft in one Room transaction. Home groups tasks into Overdue, Today, Upcoming, and Anytime. | Double-tap approval on an edited batch, close the app, stop Fastify, and reopen. Exactly the approved tasks appear once. A simulated write failure preserves the draft and creates zero tasks. Reminder intent is stored locally for delivery in Stage 6. |
| **5 · Everyday task management** | Home search, Open/Completed/All filters, collapsed completed tasks, and task detail. Support edit, complete, reopen, reschedule, delete, and brief Undo. Give each swipe shortcut a visible equivalent. | Offline, reschedule an overdue task into Today, complete it, find it under Completed, then delete and undo. Verify fields and placement after relaunch. At large text sizes, completion and opening details are separate, labeled actions. |
| **6 · Reminders throughout the Android lifecycle** | Deliver local notifications with inexact alarms. Request notification permission when the user first approves a reminder. Show disabled status and a route to system settings after denial. Reconcile alarms after edits, completion, deletion, Undo, reboot, and time-zone changes. | Exercise grant and denial separately. Denial preserves the task and shows delivery is disabled. Change time zones and verify a 9 AM reminder stays at 9 AM local. Reschedule, complete, delete, and undo while checking for duplicate or stale notifications. Explain that Android may delay delivery. |
| **7 · Settings and local-data controls** | Notification status, default reminder time, System/Light/Dark appearance, privacy explanation, and confirmed deletion of all local data. Exclude personal data from Android backup. | Change appearance and reminder defaults, restart, and verify persistence. A new default applies to future suggestions, and existing reminders keep their approved times. Confirm deletion clears tasks, draft, preferences, and pending notifications. Cancel preserves them. |
| **8 · Android v1 candidate** | An installable candidate APK and a validation record covering the full journey, accessibility, offline behavior, and remaining device limitations. | On a clean install, capture, edit, interrupt, resume, approve, deny notifications, go offline, and manage saved tasks. Repeat critical interactions with TalkBack, 200% text, predictive Back, reduced motion, landscape, and a wider layout. Record outcomes and light/dark screenshots. |

## Implementation decisions

- Use one native `:app` module. Compose screens use ViewModels and StateFlow. Room owns tasks and the single pending draft. DataStore owns preferences. Android calls Fastify only for previews, so approval and Home work offline.
- Give each pending batch a stable identity. Approval verifies and consumes that identity in the same transaction that inserts the tasks. Schedule reminders only after commit and reconcile from saved state after interruptions.
- Use the mockups to review hierarchy and interaction. Reserve primary fill for the main action, keep ordinary review rows neutral, label suggestions in words, and use functional symbols on buttons. Check keyboard reachability, system Back, and large text at each screen stage.

## Delivery, worktrees, and prompt caching

Start Stage 0 in a clean `codex/android-v1` worktree based on scaffold commit `e4deb1f`. Keep the original checkout’s staged brand assets and local reference documents separate from implementation changes.

Keep the lead in the same chat on the current model. Stage 2 is the planned parallel split. A same-model worker in a second worktree owns the Fastify preview contract, stub, and tests while the lead implements Android processing and recovery. Give the worker the three Stage 2 examples and its file boundaries. Reuse that worker for feedback. Luna was unavailable in the planning session, and cross-worker cache reuse was unverified.

At each stage, build the debug APK, run applicable unit tests and Android Lint, install the APK, and demonstrate the acceptance criteria. Add connected tests as device behavior becomes available. Record commands, results, screenshots of changed screens, and unverified cases in `validation/android.md`. Present the deliverable and stop for owner approval before committing, pushing the feature branch, or starting the next stage.
